## セキュリティ判定

**基本機能の限定公開（ソフトローンチ）なら条件付きで可能。無制限の本格公開はレート制限／ボット対策と運用監視が未整備のため保留を推奨。**「脆弱性ゼロ」「攻撃に完全耐性あり」の保証ではない。

### 046マイグレーションで適用したDB修正

- `interactions`の`anon`による行データの読み取り・挿入を禁止。
- `questions`の`anon`直接挿入を禁止。双方の古い無制限RLSポリシーも削除。
- `get_provisional_hpo_positions()`および`get_clinical_pilot_positions()`の匿名・通常認証ユーザーによる実行権限を撤回。
- `rls_auto_enable()`の通常ロールでの実行権限を撤回。
- 旧週次集計`get_weekly_constellation(date)`を`SECURITY DEFINER`に変更し、旧記録への直接SELECTを禁じても読み取り専用の集計機能は維持。
- `postgres`が今後作る関数は明示的な`GRANT EXECUTE`を必要とするよう、デフォルト権限を厳格化。
- 現在必要な公開RPCが動作し続けること、および旧権限がすべて撤回されたことをDBで再チェック。

**注意：** `supabase_admin`が作成する将来の関数に対するデフォルトEXECUTE権限も広い。今回使用したDBマイグレーションの接続ロールからは`supabase_admin`のデフォルト権限を変更できなかったため、管理者権限で別途修正する必要がある。これは現時点の露出済み関数を再び開放する問題ではなく、**将来の関数新設時の誤設定リスク**。

## 公開継続のために必要な残件

1. **投稿と分析イベントのサーバー側のレート制限／ボット対策**：Cloudflare Turnstile等によるチャレンジと、サーバー側でのトークン検証（Supabase Edge FunctionsやCloudflare Workers経由）。訪問者の端末トークンだけを信用しない。必要なシークレットの設定とプライバシー表示の確認を行う。大量の書き込みや個人の特定を伴う本番実験はしない。
2. **公開時のセキュリティヘッダー**：CSP、`frame-ancestors`、`X-Content-Type-Options: nosniff`、Referrer-Policy、Permissions-PolicyをCloudflare Pagesなどで設定する。現在のGitHub Pagesでは任意のHTTPヘッダーを細かく制御しにくいため、移行・代理配信を検討。
3. **運営アカウント保護**：GitHub 2FA/パスキー、ブランチ保護、PRレビュー、Supabase 2FA、Authのメールリンク設定と開発者許可リストの確認。ブラウザ公開の`publishable key`は秘密鍵ではない。**service_role/secret keyをリポジトリやブラウザに置かない**。
4. **サプライチェーン**：CDN配信するThree.jsとSupabase SDKを継続更新・固定、可能なら自己ホスト化とSRI/CSP。GitHub Actionsの外部アクションはcommit SHAでpinする。
5. **監視と復旧**：Supabaseの負荷・異常投稿件数・DBサイズ、日次バックアップ、非公開投稿の承認手順、コメント通報／削除依頼窓口、復旧手順。
6. **実機テスト**：iOS Safari・Android Chromeで、新規投稿、未点灯星の操作不可、ランダム紹介、週次3D、画面回転、印刷を確認。**PC用のヘッドレスChromiumによる読み取り専用の表示テストは実施済み**ですが、iPhone/Androidの実機操作、実投稿、攻撃型の負荷テストは未実施。

### 将来の記事自動追加に向けたプロンプトインジェクション対策

病気の解説を自動で更新する場合、外部Webページと申請コメントは**悪意ある命令が混じり得る未信頼コンテンツ**として扱う。検索結果やHTMLに含まれる「既存のシステム指示を無視せよ」等をツール実行命令として解釈してはいけない。

- 情報取得を公式ドメイン等に制限し、URL・ファイル内容・引用と、システム側の指示を分離する。
- AI生成物をJSONスキーマと事実出典で検証し、外部コンテンツからAPIキー・システム設定・DBへの書き込みを許可しない。
- 自動公開せずPRによる差分確認と編集承認を挟み、治療・予後の表現は原典で確認する。疑わしいテキストはそのまま公開しない。
- 生成・更新用のGitHub/Supabaseトークンは最小権限にし、別環境の機密データにアクセスさせない。

### 今回新たに修正した項目

5. **公開星座の性能面の耐性**：`048_public_star_hotpath_indexes.sql`で承認済みコメント、疾患別投稿件数、履歴日時、疾患親子のインデックスを整備。公開Web APIへの負荷が増えた場合にDBが不要な全表スキャンを繰り返すリスクを抑える。匿名ロールへのテーブルアクセス権は追加しない。
6. **本番のアクセス拒否も回帰テスト**：`public_browser_smoke.cjs`に、匿名の公開1,241件座標RPCを正の対照としたうえで、非公開研究用RPC3個・非公開テーブル4個が401/403/404となるか**読み取り専用のHTTP GET**で検証。投稿・ログイン・攻撃ペイロード送信は行わない。

### Supabase Security Advisorの解釈

[公式データベースLinter](https://supabase.com/docs/guides/database/database-linter)で次の結果を確認。

- `RLS Enabled No Policy`（情報）：非公開の投稿・疾患研究テーブルで**意図的に許可ポリシーを置かない**。個別の`SECURITY DEFINER` RPCから集計した必要な情報だけを返す構成のため、この指摘自体は誤設定ではない。
- `Public Can Execute SECURITY DEFINER Function`（警告）：来場者がログインせず星を灯す仕様では、一部の公開RPCが権限付きで実行される。固定SQLと引数の検査を確認したが、**Web APIが公開されること自体の残余リスクは継続**する。返すデータ・書き込み可能範囲は都度レビューする。
- `Unindexed foreign keys`（性能警告）：集計・星表示に関係する一部の索引を今回追加。残りはアクセス頻度を見て優先度を判断。

### 「公開できるか」の判定

- **初期段階（招待先へのソフトローンチ）**：条件付きで可能。表示・投稿・記事閲覧・週次表示の機能と、一般的なSQLインジェクション／HTML注入に対する主な防御が整っている。
- **不特定多数に向けた広告・大規模SNS拡散**：未推奨。ボットが別のUUIDを生成すれば1端末1日1投稿のルールを突破し、サイト運営の集計を汚染できる。サーバー側Turnstile検証、Edge Function/Worker経由の投稿受付、IP/ASNのレート制限、監視と復旧体制が追加で必要。
- **研究用医療データの完全非公開**：現時点で達成していない。Supabase研究用APIは認証で保護されているが、公開GitHubの`data/clinical_*.json`や過去コミットの研究ファイルは別の経路で取得し得る。完全秘匿にはデータを非公開リポジトリに隔離し、公開履歴の露出も別途処置する必要がある。
